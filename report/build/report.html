1. Idea → why this exists

A solo dev who wants a game biome today opens the Lux3D console, burns credits one asset at a time, eyeballs every mesh, hand-fixes per-engine imports, retries blind — a week per biome, and nothing is provable afterwards. AssetForge collapses that into one YAML pack brief: plan → quote → generate (Lux3D) → deterministic gates → targeted repair → engine-ready delivery with receipts.

2. What it is

  • - CLI + library (af plan|build|verify|bench) composing with the official
    • Lux3D skill conventions and the official Python SDK.
  • - Deterministic gates (stdlib GLB parser + trimesh): face-count bounds
    • (vendor 10k–300k), texture presence, sane bbox; watertight for print targets.
  • - The Repairer: one targeted prompt mutation per failed gate — the rule is
    • readable code (assetforge/mutate.py), not a black box.
  • - Receipts + offline Auditor: per-asset JSON receipts (prompt, task ID,
    • timings, gate values, sha256); python verify.py re-derives everything with zero credits, no API key, no network.
  • - Capability benchmark: bench/benchmark.md measures Lux3D's own published
    • boundary claims with N runs and a failure taxonomy.

    6. Where Lux3D is load-bearing

    Every delivered asset is a Lux3D task ID in our receipts; remove Lux3D and AssetForge has nothing to orchestrate, gate, or verify. We adopt the skill's plan→quote→REPORT conventions and the official SDK; we extend the ecosystem rather than reimplement it.

    7. The New Species case

    The organizer's own rationale — an ecosystem formed around toolchains, scenarios and developers — names exactly this layer: an installable toolchain, a measured capability map the whole platform can use, an open receipts format, and a game proving the loop end-to-end.
